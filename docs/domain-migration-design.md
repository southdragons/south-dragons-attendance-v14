## 0. 要約

1. 新しいURLは**独自サブドメイン**（例 `attend.<独自ドメイン>`。値は未決 D-1）にする。**新しいリポジトリ**から公開し、今のリポジトリ・今のURLは引き継ぎが終わるまで変えずに並行稼働させる。
2. DB・Edge Function は今の Supabase（新Supabase）を共有する。選手・予定・出欠・申請の記録はそのまま使う。
3. 保護者の編集権限は、今のURLで発行する**一度限りの引き継ぎコード**と、新しいURLでの**チームコードの入力**の2つがそろったときだけ、サーバーが新しい端末へ**複製**する。旧端末の権限はすぐには消さない。
4. 今のURLと同じ `southdragons.github.io` には、ほかに7つのPagesサイトがある。そこから匿名認証の情報が盗まれた前提で、引き継ぎが「盗んだ人に権限を移す道具」にならないように、承認が必要な条件・取り消し・管理者による監視を決める。
5. 引き継げない家庭は、今ある「端末追加申請 → 管理者承認」で復旧する。**どの家庭も、編集権限を失ったままにならない**ことを合格条件にする。
6. 7日間の管理者ログイン保持（C案）は、移行が終わってから導入する（11章）。

## 2. 脅威の整理

### 2-1. 前提とする攻撃者
| 攻撃者 | できること（前提） |
|---|---|
| T1：同じオリジンのほかのサイトに入り込んだ人（そのサイトの改ざん、依存パッケージの乗っ取り、リポジトリの権限の悪用） | 保護者がそのサイトを開いたとき、**今のURLの保存領域にある匿名ログインのセッション（アクセストークン・リフレッシュトークン）を読める**。その端末になりすまして API を呼べる |
| T2：保護者から引き継ぎコードを聞き出そうとする人 | 「コードを教えて」と頼む・偽の案内を送る |
| T3：コードを推測する人 | 新しいURLで匿名ユーザーを作り、コードを総当たりで試す |
| T4：チームコードを知っているチーム内の人 | 自分の端末で、ほかの家庭の引き継ぎを試みる |

- T1 は、**今すでに**その端末の出欠を書き換えられる。引き継ぎによって新しくできるようになってはいけないことは、次の3つ。
  1. 盗んだ権限を、本人が気づかない別の端末（新しいURL）に**長く残す**こと。
  2. 本人の引き継ぎの「枠」を先に使い、**本人を引き継げなくする**こと。
  3. 切り替えの時点で旧端末の権限が止まり、**本人が権限を失う**こと。
- サーバーは、T1 の API 呼び出しと本人の呼び出しを見分けられない（同じ有効なセッションを使うため）。したがって、**旧端末のセッションだけでは引き継ぎを完了できない**設計にする。

### 2-2. 対策の柱
| 柱 | 内容 | 主に防ぐもの |
|---|---|---|
| 2要素 | 引き継ぎの完了には、旧端末で発行したコード（旧端末の所持）と、新しい端末でのチームコードの入力（保存されていない知識）の**両方**を必要とする | T1（保存領域を盗むだけではチームコードが分からない）、T3 |
| 複製のみ | 引き継ぎは権限の**複製**。旧端末の権限は、切り替えの条件（6-3）がそろうまで止めない | T1-3 |
| 枠を奪わせない | 「1つの旧端末からの引き継ぎは1回」の上限を、本人を締め出す形にしない。2回目以降は**管理者承認**で通す | T1-2 |
| 見える化と取り消し | すべての引き継ぎを管理画面に表示し、旧端末の画面にも「この端末から引き継がれました（日時・端末の種類）」と表示する。7日間は自己取り消し、管理者はいつでも取り消せる | T1-1、T2 |
| 非常スイッチ | 不審な引き継ぎが見つかったら、管理者が「すべての引き継ぎを承認制にする」に切り替えられる（`private.feature_flags` の `transfer_requires_approval`） | T1 の大規模な悪用 |
| 推測困難・回数制限 | 3章 | T3 |

- チームコードは全家庭で共通のため、T4（チーム内の人）に対しては2要素にならない。T4 への対策は、**旧端末のコードを持っていること**と、見える化・取り消し・承認の条件（4章）による。
- 移行の前に、ほかの7つのPagesサイトを止める・依存パッケージを点検するなど、T1 の起こりやすさ自体を下げることを推奨する（D-3）。

## 3. 引き継ぎコード

### 3-1. 形式と推測困難性
| 項目 | 設計 |
|---|---|
| 生成 | Edge Function（`team`）で `crypto.getRandomValues` を使って生成する。DB関数は生成しない |
| 形式 | Crockford Base32（`0-9A-Z` から `I L O U` を除いた32文字）で10文字。表示は `XXXXX-XXXXX`。入力時は大文字化・ハイフンと空白の除去・`O→0`、`I/L→1` の読み替えをする |
| 推測困難性 | 32^10 = 2^50 ≈ 1.1×10^15 通り |
| 保存 | DBには `HMAC-SHA256(サーバーの秘密値, 正規化したコード)` だけを保存する。秘密値は Edge の Secrets（新規 `TRANSFER_CODE_PEPPER`）。平文は保存しない・ログに出さない |
| 期限 | 発行から**15分** |
| 同時に有効なコード | 1つの旧端末につき1つ。新しく発行すると前の未使用のコードは無効 |
| 発行の回数 | 1つの旧端末につき1日3回まで |

**総当たりの見積もり**（T3）
- 有効なコードが同時に最大 K = 60 個（全家庭が同時に発行した場合の上限の目安）あるとき、1回の試行で当たる確率は K / 2^50 ≈ 5.3×10^-14。
- 試行の上限を「全体で失敗1時間1,000回」にすると、1年間（約876万回）試し続けても当たる確率は約 4.7×10^-7。さらに15分の期限があるため、実際にはこれより小さい。
- 端末ごとの上限（下表）で、1台の端末からの試行は数回で止まる。

### 3-2. 試行制限
既存の `private.bump_limit` と同じ方式で、**失敗の前にカウントを確定**（コミット）してから照合する（照合の失敗で巻き戻らないようにする。チームコードの `teamCodePrepare` と同じ）。

| 範囲 | 上限（案） | 超えたとき |
|---|---|---|
| 新しい端末（匿名ユーザー）ごと | 15分に5回 | その端末からの入力を15分止める |
| IPアドレスのハッシュごと | 1時間に30回 | そのIPからの入力を1時間止める（取得できない場合は省略） |
| 全体の失敗 | 1時間に1,000回 | 全体の入力を止め、管理画面に表示する。成功した入力は数えない |
| 1つのコードへの失敗 | 制限なし（コードの値を知らない攻撃者には、どのコードへの失敗か分からないため） | — |

- 失敗の応答は、コードが「存在しない」「期限切れ」「使用済み」「別の端末に結び付け済み」のどれでも**同じ文言・同じ形**にする。

### 3-3. 1回限りの消費
1. **結び付け（新しい端末でコードを入力）**：`update private.device_transfers set target_user=$N, bound_at=now(), status='bound' where code_hmac=$H and status='issued' and expires_at>now() returning ...` を1回のトランザクションで行う。返った行がなければ失敗。**この時点でコードは使用済み**になり、ほかの端末では使えない。
2. **確認画面**：結び付けた端末にだけ、引き継ぐ子どもの名前を表示する。
3. **確定**：同じ端末が10分以内に「引き継ぐ」を押すと、権限の複製と `status='completed'` を1回のトランザクションで行う。同じ要求が2回届いても、2回目は「完了済み」を返すだけにする（同じ処理を繰り返しても結果が変わらない）。
4. 10分以内に確定しなければ `status='expired'`。コードは再利用できず、旧端末で発行し直す。

## 4. 管理者承認の要否

### 4-1. 承認なしで引き継げる条件（**すべて**満たす場合）
| 条件 | 理由 |
|---|---|
| 非常スイッチ `transfer_requires_approval` がオフ | 2-2 |
| 新しい端末で、確定の直前にチームコードを正しく入力した（`verifyTeamCode` の成功から10分以内） | 2要素（T1 対策） |
| 旧端末からの**初めての**完了した引き継ぎである | 枠を奪わせない（2回目は承認） |
| 旧端末に、承認待ちの申請（`re_registration_requests` の `pending`）がない | 申請の扱いを単純にする |
| 旧端末の、引き継ぐ権限がすべて**7日以上前から有効** | 盗んだセッションで直前に追加した権限を、そのまま運び出させない |
| 引き継ぐ選手が4人以下 | 1家庭の想定を大きく超える引き継ぎを止める（値は D-6） |
| 新しい端末が、ほかの旧端末からの引き継ぎを2件以上受けていない | 1つの端末に権限を集めさせない |
| 引き継ぎ期間中（9章の段階2〜4） | 期間外は承認制にする |

### 4-2. 承認を必須にする条件（どれか1つでも当てはまる場合）
| 条件 | 例 |
|---|---|
| 4-1 の条件のどれかを満たさない | 2回目の引き継ぎ、選手が5人以上、権限が7日未満 |
| 新しい端末でチームコードを入力できない | コードを知らない・忘れた |
| 旧端末が手元にない | 端末の紛失・故障・保存領域の消去（7章の復旧） |
| 引き継ぎが取り消されたことがある旧端末から、もう一度引き継ぐ | 争いがあった場合 |
| 非常スイッチがオン | 不審な引き継ぎが見つかったあと |

- 承認が必要な場合、確定の操作は「承認待ち」になり、権限はまだ複製しない。管理画面の「端末の引き継ぎ」に、子どもの名前・旧端末の種類と最後に使った日時・新しい端末の種類・申請日時を表示する。
- 承認待ちの引き継ぎについて、**LINE通知は送らない**（通知の通数を増やさないため。管理画面に件数を表示する。D-7）。
- 承認の操作は、重要な操作として**再認証**（管理者ログイン改善で設計した、サーバー側で強制する再認証）を求める案とする（D-8）。

### 4-3. 比較
| | 承認なし（4-1） | 承認あり（4-2） |
|---|---|---|
| 保護者の手間 | 旧URLでコードを出し、新URLで入力するだけ | 承認を待つ（管理者の対応しだい） |
| 管理者の手間 | 一覧を見て、不審なものを取り消すだけ | 1件ずつ確認して承認 |
| T1 への強さ | チームコードが漏れていなければ防げる。漏れていても、旧端末への表示・取り消し・切り替え条件で本人は権限を失わない | 管理者が本人に確認すれば防げる |
| 想定する件数 | 大多数の家庭 | 例外（紛失・2回目・大家族・不審） |

## 5. データ設計（案）

```sql
-- 引き継ぎの記録（1件 = 1回の発行）
create table private.device_transfers (
  id uuid primary key default gen_random_uuid(),
  source_user uuid not null references auth.users(id) on delete restrict,   -- 旧端末の匿名ユーザー
  target_user uuid references auth.users(id) on delete restrict,            -- 新しい端末（結び付けた時点で決まる）
  code_hmac text not null unique,                                           -- HMAC-SHA256。平文は保存しない
  status text not null check (status in ('issued','bound','pending_approval','completed','expired','cancelled','rejected','undone')),
  requires_approval boolean not null default false,
  approval_reason text,                                                     -- 4-2 のどれに当たったか
  player_ids text[] not null default '{}',                                  -- 確定時に引き継いだ選手（結び付けの時点で確定）
  team_code_verified_at timestamptz,
  issued_at timestamptz not null default now(), expires_at timestamptz not null,
  bound_at timestamptz, completed_at timestamptz,
  approved_by uuid, approved_at timestamptz,
  undone_at timestamptz, undone_by text check (undone_by in ('target','source','admin')),
  check (source_user is distinct from target_user)
);
-- 1つの旧端末で、同時に有効な（発行中・結び付け中・承認待ち）引き継ぎは1件
create unique index transfers_one_open on private.device_transfers(source_user) where status in ('issued','bound','pending_approval');

-- player_access に、どの引き継ぎで作られたかと、止めた理由を加える
alter table public.player_access
  add column source_transfer_id uuid references private.device_transfers(id),
  add column deactivated_reason text check (deactivated_reason in ('admin_revoked','transfer_undone','migrated_retired'));
```

- `player_access` の行は**削除しない**。止めるときは `active=false` と理由を記録し、戻せるようにする。
- `player_access` の `unique(player_id, auth_user_id)` により、同じ端末・同じ選手の権限は1行だけ。新しい端末がすでにその選手の権限を持っている場合（承認済みなど）は、その選手を**飛ばし**、既存の行を書き換えない。
- 引き継ぎで作る `team_members` は `method='transfer'`（`method` の制約に値を追加する）。
- `cleanup_candidates`（匿名ユーザーの整理）は、`device_transfers` に出てくる匿名ユーザーも対象から外す。
- 新しい操作（`team_api`）：`issueTransferCode`（旧端末）、`bindTransferCode` / `confirmTransfer` / `undoTransfer`（新しい端末）、`listTransfers` / `approveTransfer` / `rejectTransfer` / `undoTransferByAdmin`（管理者）。コードの生成と HMAC の計算は Edge で行い、DBにはHMACだけを渡す。

## 6. 正当な編集権限を失わせない設計

### 6-1. 原則
1. 引き継ぎは**複製**。完了しても旧端末の権限はそのまま使える（並行稼働の期間中）。
2. 権限を止める操作は、次の3つだけ。どれも**記録が残り、元に戻せる**。
   - 管理者による解除（今の `revokeDeviceAccess`）
   - 引き継ぎの取り消し（その引き継ぎで作った行だけを止める）
   - 切り替え時の旧端末の停止（6-3 の条件がそろった場合だけ）
3. 取り消しは、**その引き継ぎで作った行（`source_transfer_id` が一致する行）だけ**を止める。承認などで元からあった行には触れない。
4. 旧端末の権限を管理者が解除しても、引き継ぎ先の権限は自動では止めない（逆も同じ）。管理画面で結び付きを表示し、管理者が判断する。

### 6-2. 取り消し
| 誰が | いつまで | 結果 |
|---|---|---|
| 新しい端末（引き継ぎ先） | 完了から7日 | その引き継ぎで作った権限を止める。旧端末は変わらない |
| 旧端末（引き継ぎ元） | 完了から7日 | 同上。旧端末の画面の「この端末から引き継がれました」から操作する |
| 管理者 | いつでも | 同上。必要なら旧端末の停止（6-3）も元に戻す |

- 旧端末からの取り消しは、T1（盗んだ人）も行えてしまう。その場合に失われるのは「新しい端末の権限」だけで、旧端末の権限は残るため、本人は引き継ぎをやり直せる（2回目は承認制、4-2）。

### 6-3. 切り替え時に旧端末の権限を止める条件
段階4（9章）で、次の**すべて**を満たす旧端末の権限だけを `migrated_retired` として止める。
- 完了した引き継ぎがあり、取り消されていない。
- 引き継ぎ先の端末が、完了後に1回以上アクセスしている（`user_activity` で確認）。
- 引き継ぎ先の端末が、止める旧端末と**同じ選手**の有効な権限を持っている。
- 完了から14日以上たっている。

条件を満たさない旧端末の権限は止めず、引き継ぎを案内し続ける。止めた権限は、管理者がいつでも戻せる。

### 6-4. 不変条件（テストで確認する）
- 選手ごとの「有効な権限を持つ端末の数」は、管理者の解除・取り消し・6-3 以外の操作で**減らない**。
- 引き継ぎで、ほかの家庭の選手の権限が作られない（`player_ids` は旧端末の有効な権限と一致する）。
- 引き継ぎで、出欠・選手・予定・申請の行は変わらない。

## 7. 移行できない保護者の復旧手順（管理者承認）

### 7-1. 対象
- 旧端末を失った・壊れた・保存領域が消えた（Safariの7日の削除、端末の初期化など）。
- 旧URLを一度も開かないまま、引き継ぎ期間を過ぎた。
- 不審な引き継ぎで争いになった。

### 7-2. 保護者の操作（新しいURL）
1. 新しいURLを開く（iPhoneはホーム画面に追加したアイコンから）。
2. 「はじめての方はこちら」→ 子どもの名前を登録どおりに入力 →「すでに登録されています」と表示される。
3. 申請者名・続柄を入れて「この端末の利用を申請する」（今の端末追加申請と同じ）。

### 7-3. 管理者の操作
1. 申請の通知（今の仕組みのLINE、または管理画面）を確認する。
2. **本人確認は、申請の内容だけで判断しない。**チームで普段使っている連絡手段（顔見知りの指導者からの確認、登録済みの連絡先への電話など）で、申請したのが本人の家族であることを確かめる。
3. 確認できた子どもの申請だけを承認する（再認証を求める案、D-8）。
4. 旧端末の権限は、本人が「旧端末は使わない」と言った場合だけ、管理画面から解除する。
5. 争いがある場合：不審な引き継ぎを「取り消し」し、本人の申請を承認する。必要なら非常スイッチをオンにする。

### 7-4. 記録
- 承認・却下・取り消しは今の記録（申請の状態・`player_access` の日時と理由）に残る。管理者向けの手順書に、本人確認の方法と日付を残す欄を設ける（個人情報は手順書に書かない）。

## 8. 端末ごとの手順

**共通の注意**：コードは「**いつも使っている開き方**」で表示し、「**これから使う開き方**」で入力する。iPhoneでは、Safariとホーム画面アプリ（独立したアプリとして開く場合）の保存領域が別のため。

## 10. 2つの公開のバージョン管理・セキュリティ更新

### 10-1. 方針
| 項目 | 方針 |
|---|---|
| 正本 | 新しいリポジトリを開発の正本にする。今のリポジトリは、段階1以降は**同じコードのリリース版**を公開するだけにする |
| 同じコードを2か所に | 同じタグ（例 `v1.5.0`）を両方のリポジトリに push し、それぞれの Actions でビルド・公開する。違いはビルド時の設定（`NUXT_PUBLIC_DEPLOYMENT=legacy|primary`）だけにする。今のURL版は、引き継ぎの案内・「引き継ぎ専用」表示を出す |
| リポジトリ間の自動転送 | 使わない（相手のリポジトリに書き込める長期のトークンを置かないため）。タグの push は人の操作で行い、手順書にする |
| API の互換 | Edge・DBは1つを共有する。**今のURL版が退役するまで、その版が使う操作と応答の形を壊さない。**壊す変更は、今の `CLIENT_UPDATE_REQUIRED` の仕組みで再読み込みを促してから行う |
| 版の確認 | 画面の下部と要求ヘッダー（`x-client-version`）に版を出し、Edge で古すぎる版を検知できるようにする（任意。D-9） |
| 依存パッケージの更新 | 両方のリポジトリで Dependabot（またはそれに代わる定期確認）を有効にし、同じ版にそろえる |
| セキュリティ更新 | 正本で修正 → テスト → 同じタグを両方に公開。**両方の公開が終わるまでを1件の対応とする**（目安：重大なものは48時間以内）。片方だけの公開は「未完了」として記録する |
| CI | 両方のリポジトリで `npm test`・typecheck・Edge の `deno check` を公開の前に必ず通す（今の `pages.yml` と同じ） |
| 権限 | 両方のリポジトリで main への直接 push を禁止し、2段階認証を必須にする。Pages の環境（`github-pages`）の保護ルールを同じにする |
| 退役 | 段階5のあと、今のリポジトリはアーカイブする（Pages は案内ページだけ） |

### 10-2. 新しいドメインの安全対策
- GitHub の**ドメイン確認**（verified domain）を行い、ほかの人が同じドメインを Pages に設定できないようにする。
- レジストラ（ドメインの管理会社）のアカウントに2段階認証、**自動更新**、更新通知の受け取り先を複数にする。
- DNS は CNAME 1件だけ（サブドメイン → `southdragons.github.io` など、GitHub の案内どおり）。CAA レコードで証明書の発行元を制限することを検討する。
- 「HTTPSを強制」をオンにする。
- 新しいホスト名には、このアプリ以外を置かない（同じオリジンの問題を繰り返さないため）。
