# 父母の端末追加対応

2026年9月13日。設計書v1.5の保護者台帳・保護者アカウント管理への拡張は見送り、選手に対して複数の承認済み端末を紐づける。ここでの端末は同じブラウザの匿名認証セッションを指し、スマートフォンそのものの識別ではない。

## 利用方法

1. 最初の保護者が選手名を新規登録すると、そのブラウザに編集権限を付与する。
2. もう一方の保護者は「兄弟・選手を追加」から同じ選手名を入力する。既存選手の案内で、申請者名（1〜30文字）と続柄（父・母・祖父母・その他）を入力して端末利用を申請する。
3. 管理者が「端末追加申請」で名前と続柄を確認して承認する。本人確認は従来どおり運営者が行う。申請者名と続柄は自己申告である。
4. 承認後に申請したブラウザを更新すると、その選手が「自分の子どもだけ」に入り、既存の端末と両方から入力できる。
5. 不要・紛失端末は「チーム管理 → 参加者管理 → 対象選手の利用端末 → 権限を解除」で解除する。兄弟ごとの権限は独立している。

出欠は選手・予定につき1件。父母がそれぞれ回答を持つことはなく、最後に保存した回答を採用する。別の端末での変更は画面の「更新」で確認する。リアルタイムの同時編集・保護者別の回答集計は追加しない。

承認前の仮回答は新方式では入力できない。端末の追加承認によって既存の出欠回答を上書きしない。権限解除でも記録を削除しない。最後の1台を解除した場合も、再申請と管理者承認で利用を再開できる。

機種変更も同じ端末追加申請を使う。新しい端末で利用できることを確認後、不要になった旧端末の権限を管理者が解除する。Cookie・ブラウザデータの削除や別ブラウザの利用では別の申請が必要になる。

## 保存する情報と範囲

- `player_access`：選手、匿名認証ユーザー、申請者名・続柄、権限の有効状態、付与・解除日時。選手と認証ユーザーの組を一意にする。
- 既存の申請テーブルに申請者名・続柄を追加。未処理申請は選手と申請元端末の組につき1件にする。別端末の申請を妨げない。
- 一般画面には自分の申請と編集できる選手IDだけを返し、他の保護者名や端末情報を公開しない。利用端末一覧は管理者セッションにだけ返す。認証ユーザーIDそのものは返さない。
- 保護者台帳、メールアドレス、保護者パスワード、家族グループ、保護者ごとの通知先、自己承認は追加しない。
- 出欠・予定の保存期限は設けず、年1回見直す。将来の削除はバックアップ後。月次の匿名ユーザー整理では、解除済みを含め端末権限や申請履歴に参照されるユーザーを除外する。

## 既存データの扱い

今回の更新は選手・予定・出欠・申請・仮回答を削除しない。現在の `players.owner_id` だけを既存端末の権限として移す。過去の再登録で権限を失った元所有者を復活させない。所有者未設定の移行選手には自動で権限を与えない。

既存端末には「登録時の端末」と表示し、登録日時は今回の移行日時とする。過去の端末追加申請には名前の入力がないため、管理画面で「旧方式の申請（名前未入力）」と示す。既存の承認待ち申請も管理者が処理できるが、承認の動作は端末追加となる。旧仮回答は履歴としてDBに残し、新方式の画面には表示せず、承認時にも正式回答へ転記しない。

`owner_id` は旧記録として残すが、更新後の権限判定には使用しない。適用SQLを再実行しても、管理者が解除した権限を復活させない。

## 現在のプロジェクトへの更新順序

対象は `cuhkjnuwozgnqqqvqhnl`。既存データがあるため `setup.sql` や旧 `repair-attendance.sql` を再実行しない。

1. フロントエンドをGitHub Pagesに公開する。新しいフロントはDBが旧方式の間は旧画面・旧API形式で動く。
2. SupabaseのEdge Functionsで **team** の `index.ts` を `supabase/functions/team/index.ts` の内容に置き換えてDeployする。既存Secretsはそのまま使用する。`Verify JWT with legacy secret` は従来どおりOFF（関数内でJWTを検証）。maintenanceとLINE webhookの再配置は不要。
3. 現在のデータをバックアップする。SQL適用時は登録・出欠入力・管理操作を一時止める。
4. SQL Editorの新しいクエリに **`supabase/enable-family-devices.sql` の全体**を貼り付けて実行する。これは `migrations/20260913000000_multi_device_access.sql` と同じ内容。トランザクション内で適用し、途中のエラーでは確定しない。
5. アプリを再読み込みする。DBが返す `accessModel: multi-device` により新画面へ切り替わる。旧画面を開いたまま申請・承認した場合はDBが再読み込みを要求し、旧方式と混同した承認を防ぐ。
6. 次の操作確認を行う。LINEは既存のテスト用接続で確認し、本番LINEへは切り替えない。

バックエンド適用前は新機能の利用開始とはしない。SQL適用後に旧版関数を戻すと端末追加の権限と矛盾するため、復旧は新方式のデータを維持した修正で行う。

空の新規環境のみ `supabase/setup.sql` で初期設定と今回の変更をまとめて適用できる。

## 開発時の検証

`npm test`、`npm run typecheck`、`npx deno check supabase/functions/team/index.ts supabase/functions/maintenance/index.ts` を実行する。

DBテストは権限移行・再適用、父母両方の保存、最後の保存の採用、承認前の拒否、旧仮回答の非転記、端末ごとの解除、他の選手の拒否、直接テーブル操作の拒否、JWT・日付・退団制約、匿名ユーザー整理からの除外を確認する。クライアントのテストは旧DBとの互換性、新方式への切り替え、承認・解除APIの形式と管理情報の非公開を確認する。

適用後に直接アクセスの拒否を確認する場合：

```sh
node --env-file=.env.verification scripts/verify-access.mjs --multi-device
```

この検証は権限のない書き込みも試行するためステージング優先。匿名テストユーザー1件を作成する。実画面の操作確認は別途必要。
